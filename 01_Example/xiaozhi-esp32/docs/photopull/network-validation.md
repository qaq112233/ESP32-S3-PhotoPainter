# PhotoPull 网络与维护入口验收

本文记录 Network 模式的可重复检查项。测试不需要烧录设备；最后两项仍需在真实 ESP32-S3 和 SD 卡上执行。

## 已落实的边界

| 场景 | 预期行为 |
| --- | --- |
| SD 卡挂载失败 | 本次启动强制进入维护 AP，不使用 `nvs.net80211` 中的旧 STA 凭据 |
| SD 上有有效 Wi-Fi 凭据 | 本次启动尝试 STA；凭据不写回 Wi-Fi NVS |
| SD 无 Wi-Fi 凭据、NVS 有凭据 | 尝试 NVS 的 STA 凭据 |
| STA 首次连接超过 20 秒 | 启动 APSTA，HTTP 维护入口保持可用；后台按 5 秒、10 秒至 60 秒重试 STA |
| 用户按键进入维护 AP | 通过 Wi-Fi 任务事件切换，本次运行保持 AP，不触发重启；STA 恢复后也不自动回收该 AP |
| 自动回收维护 AP | 只有 STA 已拿到 IP 且 AP 实际客户端数为零时回收；回收前调用 `esp_wifi_ap_get_sta_list()` 校正事件队列计数 |
| 静态 HTTP GET | 只允许根路径和现有 6 个资源，并映射到固定 `/sdcard/03_sys_ap_html/` 路径；配置、令牌和任意路径均拒绝 |
| `/dataUP` POST | 首字节保留旧网络模式协议，后续 BMP 以最多 4096 字节分块写入；成功响应表示已持久化并接受显示请求 |

`ServerPort_ready()` 同时要求 HTTP 服务已注册、Wi-Fi 已启动且 AP 或 STA 已就绪。Network 模式还要求 PhotoPull 本地恢复完成及两个后台任务创建成功，失败时不会确认 OTA 的 pending image。

正常启动顺序是 PhotoPull 启动、等待本地快照恢复并排定首张图片、再初始化 Wi-Fi 和 HTTP。恢复等待有 120 秒上限；超时路径仍会启动维护 AP/Web 并保留失败返回，便于现场恢复而不会确认 OTA 镜像。

## 主机测试

执行 [README.md](README.md) 中的统一 CMake/CTest 测试。网络组直接调用生产代码中的协议与白名单辅助函数，覆盖静态资源精确白名单、配置路径拒绝、首字节单独成包、4096 字节分块、长度下溢和超限输入。它不模拟或验证 ESP32 Wi-Fi 驱动与真实网络连接。

## 固件与硬件验收

本次环境、实际构建结果和未执行项目集中记录在 [validation.md](validation.md)。

插卡测试至少覆盖：

1. SD 卡拔出或挂载失败后重启，能连接 `esp_network` 并看到内置状态页。
2. SD 配置提供有效 STA 凭据时，确认 STA 尝试发生且 `nvs.net80211` 不被写入本次凭据。
3. 错误密码等待 20 秒，确认 APSTA 可访问；STA 恢复后无客户端时 AP 回收，有客户端时 AP 保持。
4. 连续上传合法 BMP、非法 BMP、短包和超限包；合法上传返回 200，重启或刷新期间旧照片可恢复。
5. 运行中按键进入维护 AP，确认无重启，静态资源可读，`/sdcard/photopull.json` 和任意 `..` 路径均返回拒绝。
